1. Contexto Histórico & Mudança de Paradigma Evolução Arquitetural

1.1. O Problema das Plataformas Convencionais (Whaticket Clássico)

O projeto original (Whaticket open-source) foi concebido primariamente como um CRM de chat/helpdesk para múltiplos atendentes (SAC). Em sua arquitetura inicial, a captura de mensagens dependia de instâncias pesadas de navegadores automatizados (Google Chrome headless via Puppeteer). Quando aplicado à gestão de dezenas de WhatsApps corporativos simultâneos, esse modelo entrava em colapso:

Consumo Explosivo de Memória
Cada Chrome consumia entre 400 MB e 700 MB de RAM. Com 15 a 20 celulares, o servidor exigia 8 GB a 16 GB de RAM, gerando travamentos contínuos (Kernel OOM Killer) e exigindo servidores dedicados de alto custo.
Inviabilidade de Auditoria Jurídica
Quando o remetente executava "Apagar para todos", a mensagem simplesmente desaparecia do banco de dados ou quebrava a interface, eliminando provas cruciais em eventuais litígios de cobrança ou acordos.
Banimentos em Massa de Chips
Todos os WhatsApps trafegavam sob o mesmo IP público de datacenter, disparando instantaneamente as heurísticas de detecção de spam da Meta, derrubando dezenas de números em lote.
Instabilidade de Sessão e Nomes
Reconexões de rede ou reinicializações do servidor sobrescreviam nomes de WhatsApps, perdiam pareamentos e exigiam releitura diária manual de QR Codes.

1.2. O Renascimento como VERITAS: O Foco em Banco de Dados

Foi realizada uma remodelação arquitetural integral da base de código, rebatizando e refinando o sistema para VERITAS. O objetivo tornou-se um Cofre Forense de Dados & Registro Passivo de Comunicação Empresarial.

Princípio do VERITAS: "A interface web é apenas uma lente de observação; o verdadeiro coração do sistema é o banco de dados perpétuo, imutável, indexado e de alta fidelidade para custódia de transações empresariais."

3. Engenharia de Dados & Alta Performance (HPC) Banco de Dados SQLite

3.1. Diagnóstico dos Gargalos de Banco de Dados

Ao analisar a telemetria do banco de dados SQLite (`whaticket.sqlite`), identificamos que o sistema armazenava mais de 20.800 mensagens e 48.460 contatos. O banco sofria com três gargalos críticos:

Full Table Scans Contínuos
A tabela `Messages` não possuía índices em `ticketId` nem em `createdAt`. Qualquer consulta realizava varredura sequencial nas 20.800 linhas em disco.
Gargalo N+1 nas Rotas
A rota de listagem de WhatsApps disparava 115 queries SQL separadas em loop para somar contadores de mensagens e mídias de cada um dos 23 WhatsApps.
Locks Exclusivos de Escrita
O SQLite operava no modo clássico (`journal_mode = delete`). Cada mensagem travava o arquivo inteiro para leitura, congelando a interface.

3.2. As Soluções Implementadas pela Engenharia

1. Ativação do Modo WAL e Cache em RAM

PRAGMA journal_mode = WAL; -- Write-Ahead Logging: Concorrência total (Leitores não travam Escritores) PRAGMA synchronous = NORMAL; -- Reduz fsync desnecessário mantendo integridade ACID em falhas PRAGMA cache_size = -64000; -- 64 MB de cache dedicado na memória RAM para páginas quentes PRAGMA temp_store = MEMORY; -- Tabelas temporárias e ordenações executadas diretamente na RAM

2. Criação de Índices B-Tree Estratégicos

CREATE INDEX idx_messages_ticketId ON Messages(ticketId); CREATE INDEX idx_messages_createdAt ON Messages(createdAt); CREATE INDEX idx_messages_ticket_deleted ON Messages(ticketId, isDeleted); CREATE INDEX idx_tickets_whatsappId ON Tickets(whatsappId); CREATE INDEX idx_tickets_whatsapp_updated ON Tickets(whatsappId, updatedAt); ANALYZE; -- Calibração das estatísticas do otimizador de consultas

3. Eliminação do Problema N+1 com Agregação SQL Única

SELECT t.whatsappId, count(DISTINCT t.id) as totalChats, count(m.id) as totalMessages, sum(case when m.isDeleted = 1 then 1 else 0 end) as deletedMessages, sum(case when m.mediaUrl IS NOT NULL then 1 else 0 end) as mediaMessages, max(m.createdAt) as lastActivity FROM Tickets t LEFT JOIN Messages m ON m.ticketId = t.id GROUP BY t.whatsappId;
Resultado de Benchmark
41 milissegundos
O tempo de resposta para calcular as estatísticas dos 23 WhatsApps caiu de ~2.000 ms para 41 ms (um ganho de 50x de velocidade).

4. Compliance Forense, Segurança & Métricas Atuais Operação & Telemetria

4.1. Pilares de Segurança e Compliance Jurídico

Diferente de um mensageiro convencional, o VERITAS foi desenhado sob preceitos rígidos de custódia e prova jurídica:

🔒 Imutabilidade de Identidade
O nome atribuído pelo usuário ao smartphone torna-se 100% perpétuo e imutável. Nenhuma rotina de sincronização, reboot ou script tem permissão de renomear WhatsApps.
🚫 Mecanismo Anti-Delete Perpétuo
Quando qualquer participante apaga uma mensagem, o VERITAS intercepta o pacote de revogação e preserva a mensagem original intacta, carimbando com a etiqueta 🚫 MENSAGEM APAGADA.
🛡️ Anti-Ban por Isolamento de Proxy
Cada smartphone físico pode ser roteado por uma conexão proxy residencial ou 4G individual, evitando que dezenas de números compartilhem o mesmo IP.
🔍 Motor de Busca Omnisearch
Algoritmo permutacional com tolerância a 8 e 9 dígitos, formatos com ou sem DDI +55 e DDDs locais, localizando qualquer contato em menos de 5 ms.
